# 전자책 구매자 전용 매출 방향 코치 설계

## 1. 목적

`ATTEM-Studio/marketing`은 전자책 구매자가 자기 매장의 숫자를 바탕으로 목표 매출까지 필요한 고객 규모를 이해하고, 지금 가장 먼저 실행할 행동 한 가지를 정하도록 돕는 독립 웹 서비스다.

기존 `ATTEM-Studio/jangsa`의 개선은 해당 저장소에서 계속한다. 이 저장소는 기존 제품을 복제하거나 교체하지 않고, 다음 원칙만 선별해 새 제품에 적용한다.

- 복잡한 지표보다 매출 목표에서 역산한다.
- 한 번에 가장 중요한 행동 한 가지만 제시한다.
- 숫자를 보여준 뒤 의미와 다음 행동을 설명한다.
- 근거가 없는 수치를 확정값처럼 말하지 않는다.
- 실행 전후를 기록해 다음 판단으로 연결한다.

제품이 전달할 핵심 경험은 다음과 같다.

> 목표 매출까지 필요한 손님 규모가 보이고, 지금 우리 가게가 먼저 해야 할 일이 이해된다.

## 2. 대상 사용자와 접근 범위

핵심 사용자는 마케팅과 경영 숫자에 익숙하지 않은 외식업 자영업자이며, 전자책 구매자만 가입할 수 있다.

첫 가입 시 다음 정보를 받는다.

- 이름
- 이메일
- 지역
- 업체명
- 1회용 구매자 초대코드
- 필수 서비스 이용 동의
- 선택 소식 및 마케팅 수신 동의

필수 동의와 선택 동의는 분리한다. 초대코드는 한 번 사용하면 해당 이메일과 계정에 귀속한다.

## 3. 범위

### 첫 버전에 포함

- 구매자 등록과 이메일 인증
- 1회용 초대코드 검증
- 사용자 프로필과 한 개 매장 저장
- 3단계 숫자 입력 흐름
- 목표 매출 역산
- 최대 필요 신규 고객 수 계산
- 현재 병목의 근거 수준 판단
- 실행 가능한 오늘의 행동 한 가지 추천
- 실행 예정, 완료, 확인 결과 기록
- 전자책 철학을 반영한 짧은 코칭 문장
- 샘플 데이터만 사용하는 명시적 데모 모드
- GitHub Pages 빌드 및 배포 구조
- Supabase 스키마, 보안 정책, 서버 함수 구조

### 첫 버전에서 제외

- 전자책 원문 열람과 독서 진도
- 결제와 구매 내역 자동 연동
- 관리자 대시보드
- 여러 매장 관리
- 업종 평균 또는 순위 비교
- AI가 생성하는 자유형 코칭 문장
- 외부 광고 및 POS 자동 수집
- 여러 채널을 동시에 운영하도록 하는 추천
- 매출 상승 또는 상위노출 보장 표현

## 4. 기술 구조

### 프런트엔드

- Vite
- TypeScript
- 프레임워크에 종속되지 않은 작은 화면 및 도메인 모듈
- PC 우선 반응형 UI
- GitHub Actions를 통한 검사, 테스트, 정적 빌드, GitHub Pages 배포

### 인증과 데이터

- Supabase Auth: 이메일 인증 링크 방식
- Supabase Postgres: 사용자, 매장, 진단, 행동, 결과 저장
- Row Level Security: 로그인 사용자는 자기 데이터만 읽고 쓸 수 있음
- Supabase Edge Function: 초대코드 검증과 사용 처리
- 서비스 역할 키는 브라우저와 GitHub 저장소에 두지 않음

### 콘텐츠

전자책 원문을 저장하거나 보여주지 않는다. 코칭 원칙과 핵심 요약은 버전 관리되는 TypeScript 데이터 파일로 관리한다. 각 항목은 다음 필드를 갖는다.

- `key`
- `topic`
- `summary`
- `appliesTo`
- `actionKeys`
- `version`

나중에 전자책 내용이 확정되면 계산 및 추천 코드와 분리된 콘텐츠 파일만 교체할 수 있어야 한다.

## 5. 인증과 가입 흐름

1. 사용자가 이름, 이메일, 지역, 업체명, 초대코드, 동의를 입력한다.
2. 브라우저는 초대코드 원문을 저장하지 않고 Edge Function으로 전송한다.
3. 서버는 해시로 저장된 유효 코드인지, 미사용 상태인지, 요청 제한을 통과했는지 확인한다.
4. 유효하면 초대코드를 이메일에 임시 귀속하고 인증 링크를 발송한다.
5. 사용자가 이메일 링크로 돌아오면 Auth 계정과 프로필을 연결하고 접근 상태를 `active`로 바꾼다.
6. 이후 로그인은 이메일 인증 링크만 사용한다.
7. 인증되지 않았거나 접근 상태가 활성화되지 않은 계정은 진단과 기록 데이터에 접근할 수 없다.

오류 문구는 초대코드 존재 여부나 다른 구매자의 이메일을 노출하지 않는다. 예: `코드를 확인할 수 없습니다. 입력 내용을 다시 확인해 주세요.`

## 7. 입력 모델

### 필수

- 최근 월평균 매출

월 고객 수 또는 주문 수가 있으면 직접 사용한다. 없으면 `최근 월평균 매출 / 평균 객단가`로 계산한 값을 추정 고객 수로 표시한다.

### 선택

- 월 방문 고객 수
- 월 주문 수
- 신규 고객 수 또는 비중
- 재방문 고객 수 또는 비중
- 재방문 데이터를 확인하는 출처
- 광고비
- 광고 클릭 수
- 광고로 방문한 실제 신규 고객 수
- 노출, 플레이스 클릭, 길찾기, 전화, 예약 수
- 요일별 및 시간대별 매출
- 현재 운영 채널
- 홍보 수신동의를 받은 고객 DB 유무
- 메뉴와 가격을 변경할 수 있는지

## 8. 계산 규칙

### 8.1 부족 매출

```text
부족 매출 = max(목표 월 매출 - 최근 월평균 매출, 0)
```

현재 매출이 목표 이상이면 추가 유입보다 이익, 객단가, 재방문, 운영 효율을 우선 검토한다.

### 8.2 최대 필요 신규 고객

```text
최대 필요 신규 고객 수 = ceil(부족 매출 / 평균 객단가)
일평균 최대 필요 신규 고객 수 = ceil(최대 필요 신규 고객 수 / 월 영업일 수)
```

이 값은 목표를 전부 신규 고객으로 채운다고 가정한 상한 시나리오다. 확정 예측이나 광고 목표로 표현하지 않는다.

결과 문구 예시는 다음과 같다.

> 목표를 전부 신규 고객으로 채운다고 가정하면 최대 400명이 더 필요합니다. 실제로 재방문과 객단가 개선이 포함되면 필요한 신규 고객 수는 줄어듭니다.

### 8.3 목표 분배

사용자가 원하면 부족 매출을 다음 항목에 직접 나눌 수 있다.

- 신규 고객 증가
- 재방문 증가
- 평균 객단가 상승

제품은 근거 없는 기본 비율을 자동 제시하지 않는다. 분배하지 않으면 전부 신규인 상한 시나리오만 보여준다.

### 8.4 광고 역산

방문 전환율과 클릭 비용을 실제로 입력한 경우에만 다음 값을 계산한다.

```text
필요 클릭 수 = 신규 방문 목표 / 확인된 방문 전환율
예상 광고비 = 필요 클릭 수 * 평균 클릭 비용
고객 획득 비용 = 광고비 / 광고로 확인된 실제 신규 고객 수
```

방문 전환율 또는 실제 광고 유입 고객 수가 없으면 광고비를 확정 계산하지 않고 측정 행동을 추천한다.

## 9. 재방문 데이터 처리

정확한 재방문 판단에는 같은 고객의 이전 방문과 현재 방문을 연결하는 식별 가능한 기록이 필요하다. POS 회원, 예약, 주문, 스탬프, 고객 프로필처럼 방문 이력을 연결할 수 있는 출처가 있는 경우만 `확인됨`으로 취급한다.

재방문 데이터 상태는 다음 세 가지다.

- `known`: 연결된 방문 이력으로 확인
- `sampled`: 제한된 기간의 표본 또는 현장 질문
- `unknown`: 확인할 수 없음

`sampled`는 확정 재방문율이 아니라 참고 지표로만 사용한다. `unknown`이면 재방문 병목을 계산하거나 점수화하지 않는다.

재방문 데이터가 없을 때의 기본 동작은 다음과 같다.

- 필요 고객 수는 전부 신규인 최대치로 표시
- 재방문 병목은 진단 후보에서 제외
- 고객 수용 여력과 필요한 일평균 고객 수를 먼저 비교
- 수용하기 어려우면 객단가와 운영 효율을 함께 검토하도록 안내
- 재방문 판단이 실제 추천을 바꿀 수 있을 때만 후속 측정 행동 제안

단순 현장 질문은 현재 방문자의 구성만 보는 표본이므로 핵심 재방문율 계산에 사용하지 않는다.

## 10. 병목 진단

사용자에게는 다음 다섯 영역만 보여준다.

1. 노출
2. 클릭
3. 방문
4. 객단가
5. 재방문

각 병목은 `판단 가능`, `일부 가정`, `정보 부족` 상태를 가진다. 데이터가 없는 병목은 0점 처리하지 않고 비교 대상에서 제외한다.

업종 평균과 퍼센타일은 유효한 표본 데이터가 준비되기 전까지 사용하지 않는다. 첫 버전은 사용자의 전후 데이터와 직접 입력한 사실만 사용한다.

## 11. 행동 추천

추천 후보는 다음 요소를 함께 평가한다.

- 매출 영향 가능성
- 문제의 긴급성
- 근거 수준
- 현재 실행 가능성
- 비용 부담
- 예상 소요 시간
- 실행 후 측정 가능성
- 선행 작업 필요 여부

다음 조건은 점수보다 먼저 적용한다.

- 데이터가 부족한 유료 행동은 제외
- 고객 수용 여력이 없으면 신규 유입 행동 제외
- 수신동의 고객 DB가 없으면 메시지 발송 행동 제외
- 메뉴 변경이 불가능하면 메뉴 구성 행동 제외
- 재방문 데이터가 없으면 재방문 병목 단정 제외

최종 결과는 가장 높은 우선순위의 실행 가능한 행동 한 가지만 보여준다. 보조 행동은 첫 버전에서 노출하지 않는다.

추천 카드 구조는 다음과 같다.

- 현재 문제
- 판단 근거
- 오늘의 행동
- 실행 방법 3단계
- 예상 시간과 비용 수준
- 확인할 숫자 하나
- 결과 확인 날짜
- 하지 말아야 할 행동

- `scheduled_for`
- `check_in_due_at`
- `created_at`
- `updated_at`

### `check_ins`

- `id`
- `user_id`
- `action_plan_id`
- `before_value`
- `after_value`
- `note`
- `recorded_at`

모든 사용자 데이터 테이블은 `user_id = auth.uid()` 기준의 RLS 정책을 적용한다.

## 13. 오류와 복구

- 필수 숫자가 없거나 0이면 계산 대신 필요한 값을 안내한다.
- 선택 데이터가 없으면 관련 계산과 진단만 제외한다.
- Supabase 연결에 실패하면 개인정보를 로컬 저장소에 대신 저장하지 않는다.
- 인증 세션이 만료되면 입력값을 서버로 보내기 전에 재로그인을 안내한다.
- 중복 제출은 서버에서 멱등 처리한다.
- 초대코드 검증은 요청 제한을 적용하고 구체적인 실패 원인을 외부에 노출하지 않는다.
- 데모 모드는 빌드 환경에서 명시적으로 켤 때만 동작하며 실제 개인정보 입력을 받지 않는다.

## 14. 보안과 개인정보 원칙

- 서비스 역할 키와 초대코드 원문을 클라이언트 번들에 포함하지 않는다.
- 공개 URL과 공유 문구에 매출, 광고비, 이메일을 넣지 않는다.
- 필수 동의와 선택 마케팅 동의를 분리한다.
- 프로필과 진단 데이터의 보관 목적을 가입 화면에서 설명한다.
- 민감한 원본 데이터를 로그에 기록하지 않는다.
- 실제 운영 전 개인정보 처리방침과 보관 및 삭제 절차를 운영 주체가 검토한다.

## 15. 테스트와 완료 기준

### 계산

- 부족 매출 계산
- 전부 신규인 최대 필요 고객 수와 영업일 환산
- 목표 달성 상태
- 객단가 또는 영업일이 0인 입력
- 직접 분배 합계 검증
- 광고 전환 데이터가 없는 경우 비용 계산 금지

### 추천

- 재방문 데이터가 없으면 재방문 병목을 단정하지 않음
- 수용 여력이 없으면 신규 유입 행동 제외
- 광고 데이터가 부족하면 유료 확대 행동 제외
- 수신동의 DB가 없으면 발송 행동 제외
- 화면에는 오늘의 행동 한 가지만 표시

### 인증과 데이터

- 유효, 만료, 사용 완료 초대코드 처리
- 이메일 인증 전 접근 차단
- 사용자별 데이터 격리
- 로그아웃과 세션 만료 처리
- 선택 마케팅 동의를 거부해도 서비스 이용 가능

### 화면

- 키보드로 가입과 진단 완료 가능
- 입력 오류가 해당 질문 가까이에 표시됨
- 결과를 10초 본 뒤 행동과 확인할 숫자를 식별 가능
- PC 우선 레이아웃과 기본 모바일 반응형 동작

### 배포

- 형식 검사, 타입 검사, 단위 테스트, 정적 빌드 성공
- GitHub Pages 경로에서 새로고침과 자산 로딩 성공
- 환경 변수가 없는 데모 빌드에 비밀값이 포함되지 않음

## 16. 첫 구현 단위

첫 구현은 다음 순서로 한 번에 검증 가능한 기반을 만든다.

1. Vite 및 TypeScript 프로젝트와 자동 검사
2. 공통 디자인 토큰과 시작 화면
3. Supabase 클라이언트 경계, 환경 설정 예시, 데모 어댑터
4. 가입, 초대코드, 이메일 인증 화면
5. 데이터베이스 마이그레이션, RLS, 초대코드 Edge Function
6. 3단계 진단 입력과 검증
7. 순수 계산 모듈과 최대 필요 신규 고객 표시
8. 규칙 기반 단일 행동 추천
9. 개인 홈과 실행 기록
10. GitHub Actions와 Pages 배포

Supabase 프로젝트 값이 설정되지 않은 상태에서는 샘플 데이터 전용 데모로 전체 화면을 확인한다. 실제 이메일 인증, 초대코드 사용, 사용자 데이터 저장은 운영자가 Supabase 프로젝트를 만들고 공개 클라이언트 설정과 서버 함수를 배포한 뒤 활성화한다.

## 17. 주요 위험과 대응

- **초대코드 노출:** 원문 미저장, 서버 검증, 1회 사용, 요청 제한으로 대응한다.
- **정적 배포의 보안 오해:** 브라우저는 신뢰 경계가 아니며 권한 판단은 Supabase RLS와 Edge Function에서 수행한다.
- **부족한 데이터로 과도한 코칭:** 모르는 값은 제외하고 정보 부족 행동을 우선한다.
- **전부 신규 가정의 오해:** 항상 `최대`, `상한 시나리오`로 표시하고 광고 예산으로 직접 변환하지 않는다.
- **전자책 내용 변경:** 콘텐츠 데이터와 계산 및 추천 코드를 분리한다.
- **기존 jangsa와 기능 중복:** 저장소와 배포를 분리하고 검증된 원칙만 재구현한다.
- **초기 범위 확대:** 결제, 관리자, AI, 원문 열람, 다중 매장을 첫 버전에서 제외한다.

# 집중형 진단 위저드 디자인

## 목표

장사네비게이션 진단 화면을 긴 설문 문서가 아니라, 사용자가 코치와 대화하듯 한 질문씩 답하는 3단계 반응형 위저드로 바꾼다. 기본 진단은 짧게 유지하고, 요식업 운영 정보를 아는 사용자는 선택 입력을 통해 고객 확보 문제와 매장 수용력 문제를 더 정확히 구분할 수 있게 한다.

## 현재 문제

- 모든 `step-panel`이 동시에 표시되어 화면이 지나치게 길다.
- 현재 진행 중인 챕터와 다음 행동의 구분이 약하다.
- 모바일에서 질문과 버튼이 한 화면에 과도하게 이어져 피로도가 높다.
- 한글 문장이 컨테이너 끝에서 어색하게 끊기는 경우가 있다.

## 선택한 방향

현재 챕터만 보여주는 집중형 단계 카드 안에서 질문을 한 번에 하나씩 보여주는 대화형 코칭 방식을 사용한다.

- 1단계: 매출 목표
- 2단계: 현재 고객 상황
- 3단계: 실행 조건

각 단계는 하나의 독립된 화면처럼 보이지만 동일한 폼 안에서 동작한다. 챕터 안에서도 현재 질문만 강조하고, 답변 후 다음 질문으로 이동한다. 이전·다음 이동 시 입력값은 유지하며, 현재 필수 질문이 유효할 때만 다음 질문으로 넘어간다.

## 코칭 문장 원칙

- 시스템 용어보다 대표님이 일상적으로 사용하는 표현을 쓴다.
- 질문 아래에 답변 목적과 입력 기준을 한 문장으로 설명한다.
- 정확한 값을 모를 수 있다는 점을 먼저 인정하고, 구간 선택 또는 `잘 모르겠어요`를 제공한다.
- 숫자를 입력하면 다음 질문 전에 한 줄짜리 해석을 보여준다.
- 해석은 판단이나 질책이 아니라 현재 상태와 다음 계산의 의미를 알려준다.

예시:

> 최근 한 달 평균 매출은 어느 정도인가요? 정확하지 않아도 괜찮아요. 가장 가까운 금액을 적어주세요.

> 목표까지 월 1,000만 원이 더 필요해요. 현재 객단가라면 하루 약 20명의 추가 고객이 필요합니다.

## 화면 구조

### 공통

- 상단 작업 헤더에 현재 단계, 챕터 이름, 전체 진행률을 표시한다.
- 본문에는 현재 단계의 제목, 짧은 설명, 현재 질문만 강조해서 표시한다.
- 답변 직후 현재 값의 의미를 보여주는 짧은 코칭 피드백 영역을 둔다.
- 하단 행동 영역에는 이전·다음 질문 또는 결과 보기 버튼을 배치한다.
- 선택형 답변은 충분한 터치 영역을 가진 카드 형태를 유지한다.
- 선택 입력과 비교 수치는 접을 수 있는 보조 영역으로 남긴다.

## 챕터별 기본 질문

### 1장 · 목표 매출

1. 최근 한 달 평균 매출
2. 목표 월 매출
3. 평균 객단가
4. 월 영업일 수

입력값을 바탕으로 목표까지 필요한 월 추가 매출과 하루 추가 고객 수를 즉시 해석한다.

### 2장 · 현재 고객 상황

1. 월 고객 수를 알고 있는지
2. 현재 가장 고민되는 부분
3. 신규·재방문 고객 정보를 알고 있는지

수치를 모르면 `정확히 알아요`, `대략 알아요`, `잘 모르겠어요` 중 하나로 답할 수 있게 한다. 모르는 값을 임의로 추정하도록 강요하지 않는다.

### 3장 · 실행 조건

1. 추가 고객을 받을 여력이 있는지
2. 메뉴 또는 가격 변경이 가능한지
3. 동의받은 고객 연락처나 연결된 방문 이력이 있는지
4. 광고를 운영하고 있는지

이 답변은 추천 행동이 광고, 재방문 관리, 객단가 또는 운영 효율 중 어디를 우선해야 하는지 제한하는 조건으로 사용한다.

## 요식업 상세 분석 선택 입력

기본 흐름을 방해하지 않도록 관련 질문 아래에 `우리 가게 운영 정보로 더 정확히 계산하기` 펼침 영역을 둔다. 모든 항목은 선택 사항이며 비워도 기본 진단을 완료할 수 있다.

초기 버전에서는 실제로 답하기 쉽고 계산에 직접 쓰이는 여섯 항목만 사용한다.

1. 전체 좌석 수
2. 하루 홀 영업시간
3. 가장 붐비는 시간의 좌석 점유 정도: 여유 있음, 절반 정도, 거의 참, 웨이팅 발생
4. 한 팀의 평균 인원
5. 평균 체류시간: 30분 이하, 30~~60분, 60~~90분, 90분 이상, 잘 모름
6. 홀·포장·배달 매출 비중

테이블 수는 크기가 달라 수용 능력을 왜곡할 수 있으므로 전체 좌석 수를 우선한다. 대표님이 직접 회전율을 계산하게 하지 않고, 홀 영업시간과 체류시간을 조합해 이론상 좌석 회전 구간을 계산한다. 평균 팀 인원은 필요한 고객 수를 하루 추가 팀 수로 바꾸는 데 사용한다.

예약률, 웨이팅 건수, 직원 수와 같은 추가 항목은 초기 버전에서 제외하고 실제 사용 데이터와 문의를 확인한 뒤 확장한다.

## 상세 분석 결과

상세 정보가 충분하면 결과를 두 축으로 나눈다.

- 고객 확보 여력: 목표 달성에 필요한 추가 고객 수
- 매장 수용 상태: 현재 운영 조건과 혼잡도를 바탕으로 한 `여유`, `시간대 제약`, `포화` 분류

두 값을 비교해 추천의 우선순위를 정한다.

- 좌석 점유가 여유 있거나 절반 정도이면 신규 고객 확보 또는 재방문 행동을 우선한다.
- 거의 차거나 웨이팅이 발생하면 광고 확대 전에 체류시간, 시간대 분산, 포장·배달 구조 개선을 우선한다.
- 필요한 하루 추가 고객 수는 평균 팀 인원으로 나누어 `하루 추가 팀 수`도 함께 보여준다.
- 홀 영업시간과 체류시간이 모두 있을 때만 이론상 좌석 회전 구간을 참고 정보로 보여준다.
- 상세 정보가 부족하면 수용 가능한 고객 수를 단정하지 않고 기본 고객 수 계산만 제공한다.

결과 예시:

> 목표 달성에는 하루 약 12명, 평균 4인 팀 기준으로 3팀이 더 필요해요. 가장 붐비는 시간에도 좌석이 절반 정도 차므로, 현재는 좌석 확대보다 신규 고객 확보가 먼저입니다.

이론상 좌석 회전은 `홀 영업시간 ÷ 평균 체류시간`의 구간으로 계산한다. 이는 실제 고객 수 예측이 아니라 물리적 상한을 이해하기 위한 참고치로만 표시한다. 좌석 수, 직원 처리 속도, 주문 집중도 등으로 실제 수용량이 달라질 수 있음을 함께 알리고 매출이나 성과를 보장하는 표현을 사용하지 않는다.

### 모바일

- 한 열 레이아웃을 사용한다.
- 화면 좌우 여백을 줄이고 입력·선택·버튼을 전체 너비로 표시한다.
- 진행 정보는 짧게 유지하며 행동 버튼이 질문과 명확히 분리되도록 한다.
- 최소 44px 이상의 조작 영역을 제공한다.

### PC

- 질문을 읽기 좋은 중앙 폭으로 제한한다.
- 카드 내부 여백과 질문 간격을 넉넉하게 사용한다.
- 숫자 입력은 의미가 연결된 항목끼리 2열로 배치하되, 선택 질문은 읽기 편한 폭을 유지한다.

## 단계 전환

- 비활성 단계에는 `hidden`을 적용하고 스타일에서도 강제로 노출되지 않도록 보장한다.
- 단계가 바뀌면 진행률, 단계 번호, 챕터 이름을 함께 갱신한다.
- 새 단계의 제목으로 초점을 이동해 화면 읽기 도구와 키보드 사용자가 현재 위치를 알 수 있게 한다.
- 질문 간 이동에서는 새 질문 제목으로 초점을 옮기고 현재 질문 번호도 함께 알린다.
- 짧은 페이드·상승 전환을 사용하며 `prefers-reduced-motion` 환경에서는 애니메이션을 제거한다.
- 이전 단계로 돌아가도 입력값과 선택값을 그대로 유지한다.

## 문장 가독성

- 설명과 선택지에는 한글 어절 중심 줄바꿈을 적용한다.
- 버튼 문구와 짧은 라벨은 불필요하게 두 줄로 갈라지지 않도록 한다.
- 긴 내용은 임의로 작게 축소하지 않고 컨테이너 안에서 자연스럽게 줄바꿈한다.

## 오류 처리

- 현재 단계의 필수값이 없거나 잘못되면 단계 이동을 막는다.
- 첫 번째 오류 항목으로 초점을 옮기고 해당 항목 가까이에 오류 문구를 표시한다.
- 숨겨진 단계의 오류나 입력값을 임의로 초기화하지 않는다.
- 선택 상세 입력이 비어 있거나 `잘 모름`이어도 오류로 처리하지 않는다.
- 홀·포장·배달 비중을 모두 입력한 경우에만 합계가 100%인지 검증한다.
- 저장 실패와 제출 중 상태에 관한 기존 동작은 유지한다.

## 테스트

- 최초 진입 시 1단계만 보이는지 확인한다.
- 각 챕터에서 현재 질문만 강조되고 답변 후 다음 질문으로 이동하는지 확인한다.
- 유효한 입력 후 다음 단계로 이동하면 이전 단계는 숨고 새 단계만 보이는지 확인한다.
- 이전으로 돌아갔을 때 입력값이 유지되는지 확인한다.
- 진행률과 챕터명이 단계에 맞게 갱신되는지 확인한다.
- 상세 분석을 열지 않아도 기본 진단을 완료할 수 있는지 확인한다.
- 상세 운영 정보를 입력하면 고객 확보 여력과 수용 여력이 구분되는지 확인한다.
- 상세 정보가 부족할 때 수용력 수치를 단정하지 않는지 확인한다.
- 매출 비중을 모두 입력했을 때만 합계 검증이 적용되는지 확인한다.
- 모바일 반응형 규칙, 한글 줄바꿈, 동작 영역 크기에 대한 스타일 계약을 확인한다.
- 기존 진단 계산·검증·저장 테스트 전체를 실행해 회귀가 없는지 확인한다.

## 범위 제외

- 데이터베이스 구조 변경
- 로그인 및 초대 코드 흐름 변경
- 새로운 챕터 추가
- 예약률, 웨이팅 건수, 직원 수를 이용한 운영 분석
